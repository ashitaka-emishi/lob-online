## Phase 2: Path Cost — Charge Submitted Path (#675)

Add `pathCost` to `movement.js` and switch `resolveMove` to compute MP cost from the
submitted `path[]` rather than the Dijkstra optimal path.

### Tasks

- [x] Task 2.1: Add `export function pathCost(path, formation, scenario, mapData, hexIndex = null)`
      to `movement.js`. The function walks `path[]` pair-by-pair: calls `getDirectionBetween` for
      each step (throwing → returns `Infinity` for non-adjacent pairs) then calls
      `hexEntryCostBreakdown` to accumulate cost. Returns `Infinity` if any step is impassable.
      Cite `// LOB §3 — charge cost of actually-entered hexes, not Dijkstra optimal`.
- [x] Task 2.2: In `resolveMove`, replace the `movementPath` call with:
  1. `pathCost(path, formation, scenario, ctx.mapData, ctx.hexIndex)` to get actual route cost.
  2. Throw `INVALID_MOVE` if the result is `Infinity` (impassable or non-adjacent step).
  3. Throw `INSUFFICIENT_MPS` if cost exceeds `unit.remainingMPs`.
  4. Charge `pathResult` (the pathCost result) when updating `movedUnit.remainingMPs`.
     Remove the `movementPath` import if it is no longer used.
- [x] Task 2.3: Write/extend tests for `pathCost` in `movement.test.js`:
  - Returns correct sum for a valid multi-hex path.
  - Returns `Infinity` for a path containing a non-adjacent hex pair.
  - Returns `Infinity` for a path through an impassable hexside.
- [x] Task 2.4: Write/extend MOVE handler tests:
  - Path through expensive terrain charges more than the Dijkstra optimal (demonstrates fix).
  - Path with impassable mid-route hex is rejected with `INVALID_MOVE`.
