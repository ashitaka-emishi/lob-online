# Specification: MOVE Debt Sprint — Path Cost + Partial Moves (#675 #680)

**Track ID:** move-debt-sprint_20260627
**Type:** Bug

## Summary

Fix two rules-correctness gaps in the MOVE action handler deferred from PR #674: charge the
actual submitted-path MP cost rather than the Dijkstra optimal cost (#675), and allow a unit to
make multiple MOVE actions in the same activation by tracking the activated roster instead of
checking `unit.hex === activation.hex` (#680).

## Context

Both issues were surfaced during the M9 MOVE action track (PR #674) team-review and deferred
with a debt score of 3 each. Both are in `server/src/engine/actions/move.js` and relate to
LOB §3 movement rules. The fixes are tightly coupled — #680 (roster gate) is a prerequisite
for #675 (path cost) to be fully testable, because without partial-move support a unit can
only make one MOVE per activation and the path-cost discrepancy is less visible.

## Problem Description

### #675 — Dijkstra cost charged instead of submitted-path cost

`resolveMove` calls `movementPath(unit.hex, destination, ...)` which computes the Dijkstra
optimal cost to the destination and charges that — ignoring the intermediate hexes in
`payload.path[]`. Under LOB §3, a unit pays the cost for the hexes it actually enters.
A player routing through expensive terrain is undercharged; a path through an impassable
mid-route hex is accepted if any other route to the destination exists.

### #680 — Second MOVE call rejected mid-activation

`resolveMove` guards `unit.hex === activation.hex` (line 42). After a unit's first MOVE,
its hex is the destination — no longer the activation hex — so any second MOVE call throws
`INVALID_ACTION`. LOB §3 explicitly allows a unit to split its MPs across multiple MOVE
actions in the same activation. `remainingMPs` already tracks the balance correctly; only
the guard is wrong.

## Acceptance Criteria

- [ ] A MOVE action charges the sum of `hexEntryCost` for each step in `payload.path[]`, not the Dijkstra optimal cost.
- [ ] A path that traverses an impassable hexside is rejected with `INVALID_MOVE`, not accepted because an alternative route exists.
- [ ] A unit in the activated roster can make a second MOVE action in the same activation, paying cost from its remaining MPs.
- [ ] A unit not in the activated roster is rejected with `INVALID_ACTION`.
- [ ] `handleActivateStack` stores the activated roster in `currentActivation.activatedUnitIds`.
- [ ] Existing MOVE action tests remain green; new tests cover both fixed behaviors.

## Technical Notes

`getDirectionBetween` is a private helper in `movement.js`. Rather than exporting it, a new
`pathCost` function in `movement.js` encapsulates the pair-by-pair walk and returns the total
cost (or `Infinity` if any step is non-adjacent or impassable). This keeps the direction-index
logic co-located with the hex geometry code.

For #680, `unitsInHex` must be computed unconditionally in `handleActivateStack` (currently it
is inside the `if (movementAllowances)` block), so the roster is always available even in
test-stub environments without scenario injection.
