# Specification: M8 Faction Binding — Derive Player Side from Token, Enforce on Join/Re-Join

**Track ID:** m8-faction-binding_20260624
**Type:** Chore
**Created:** 2026-06-24
**Status:** Draft
**Closes:** #562, #563

## Summary

`requireSide` currently validates that a session token matches either DB token but never derives
which faction that token belongs to — it trusts the session-stored `side` string instead.
This track fixes that: derive the authoritative player side from the token/faction columns in
the DB, expose it as `req.side` for all guarded routes, and enforce it at the join/re-join path
so duplicate faction selection is rejected.

## Context

The SQLite `games` table has `side_a_token`/`side_b_token` and `side_a_faction`/`side_b_faction`
columns (both pairs populated at create/join time). `requireSide` checks that
`player.sideToken` matches one of the two token columns, but then sets `req.game` without
exposing which side that token belongs to. Route handlers read `player.side` from the session
(set from the request body at join time) for authorization — a mismatch between session and
DB is possible if sessions are replayed or logic bugs exist.

The join route also does not prevent two players from choosing the same faction: the second
player's `side` is written to `side_b_faction` without checking whether `side_a_faction`
already holds that faction value.

The re-join path compares `existingSession.side` against the requested `side` to block
side-switching, but that check trusts the session-stored string rather than the DB-bound
faction for the token.

No DB migration is required — the faction columns exist and are already populated.

## Acceptance Criteria

- [ ] `requireSide` derives the caller's side from which token column matched and the
      corresponding faction column; populates `req.side` before calling `next()`
- [ ] All guarded route handlers (`GET /:id`, `GET /:id/actions`, `POST /:id/actions`) use
      `req.side` for authorization, never `player.side`
- [ ] `POST /:id/join` (new join) rejects with 409 if the requested side is already held by
      the creator (`side_a_faction === requested side`)
- [ ] `POST /:id/join` (re-join) derives the DB-bound faction for the session token and
      rejects with 403 if the requested `side` does not match
- [ ] Existing auth test coverage for `requireSide` extended to assert `req.side` is set
- [ ] `npm run test` passes with no new warnings

## Technical Notes

- `requireSide` already reads `row.side_a_token` and `row.side_b_token` for the token check
  (lines 41–43). The derived side is a simple conditional: if `player.sideToken ===
row.side_a_token` then side = `row.side_a_faction`, else side = `row.side_b_faction`.
- `req.side` is the authoritative side string for the request; `player.side` from the session
  becomes read-only context (used only for `setPlayerSession` on re-join to preserve the
  session contract).
- The join-path duplicate-faction check belongs in the route handler (before `joinGame` is
  called), not in the store — the store's `updateJoin` already fails atomically if the game
  is not open.
- `games.test.js` mocks `getPlayerSession` — the mock return value needs `sideToken`
  matching one of the two tokens in the `getGame` mock for `req.side` to be set correctly.
  Existing tests already do this (`sideToken: 'tok'` matches `side_a_token: 'tok'`).
