## 15:58 — PR: M5 Debt Cleanup Sprint (#482 #481 #487 #486 #467 #468 #470 #440)

This PR closes all eight actionable score-2 debt items that remained open after PR #489 merged the score-3 findings from M5. The motivation was to clear the debt register before M6 combat work begins — going in with known deficiencies in the server action route, the OOB editor widget, and the map edge model would have made M6 harder to review and riskier to test. The sprint was scoped tightly: five commits, no schema or auth boundary changes, and a strict "zero new debt" budget enforced throughout.

The most substantive change is in the `CounterImageWidget`. Issue #486 removed the internal path-prefix detection that derived `side` by parsing `nodePath` segments — a fragile heuristic that silently broke when paths didn't follow the expected `<side>.<level>.<index>` pattern. The widget now accepts an explicit `side` prop and `OobDetailPanel` passes it from its own `side` computed property. This is the cleaner boundary: the parent that knows the side tells the child, rather than the child guessing from a string. Issue #487 adds a `@focusout` handler that clears `activeFace` when focus leaves the widget entirely, using `relatedTarget` / `currentTarget.contains()` to distinguish true blur from within-widget focus movement. Without this, the Arrow-key listener on `window` stayed active after the user tabbed away, suppressing page scrolling.

The edge-model work (issues #467, #468, #470) was three related fixes across client and server. The test suite for `stripNonPlayableBoundaryEdges` previously only exercised canonical faces 0–2 from an odd-column hex, leaving the S/SW/NW directions (faces 3–5 as seen from a non-playable hex — stored as faces 0–2 on adjacent hexes) and even-column parity completely untested. Seven new tests fill that gap, including an explicit "negative parity" case that verifies playable-to-playable edges are preserved. The map editor now shows a brief status-bar notice when a non-playable boundary click is silently discarded and when edges are stripped at save-time. The server-side strip on `PUT /data` was wired via a new `transform` option on `editorRouteFactory`, keeping the factory generic while letting `mapEditor.js` inject the domain-specific stripping logic using `hexNeighborInDir` from the server hex engine.

For issue #482, adding the `io` null guard in `POST /actions` was trivially small but covered an important correctness gap: a successfully committed state change was producing a 500 because `req.app.locals.io` could be absent in environments where Socket.io hadn't attached yet. The test additions for #481 were larger — seven distinct coverage gaps across `games.test.js`, `gameSocket.test.js`, and `UnitStatsPanel.test.js`, including the `select-unit` Vue component emit contract and the `game:leave` intentional-no-auth-check documentation.

Issue #440 (parallelizing the two `loadGame` fetches) was resolved as a documented blocker rather than a code change. `scenarioId` is only known after `state.scenarioId` returns from the game-state response, so the map-config URL cannot be constructed until the first fetch resolves. The API would need to embed `scenarioId` in the join payload or a route param to enable `Promise.all`. A comment was added at the call site explaining this constraint so the next reader doesn't spend time rediscovering the same dead end.

## 18:42 — PR: Pre-M6 Debt Score Sprint — Reduce Cumulative Score to < 15

This PR closes 12 tech-debt issues (29 score points) across four logical groups, bringing the net open debt score from 31 to 16 before M6 combat work begins. The sprint was planned because 6 additional open issues (#467 #468 #470 #481 #486 #487) were not yet reflected in the register from prior sprint work, making the true score approximately 43 — an unsustainable level to carry into a milestone that will add its own debt. Each phase could have been merged independently, but the scope was tight enough to ship as one PR without meaningful review risk.

Phase 1 addressed the four ActionPanel findings from the PR #493 review. The accessibility work (#497, #498) follows the pattern already established in `UnitStatsPanel`: a visually hidden `aria-live="polite"` region announces turn-handoff transitions so screen readers catch state changes that are otherwise conveyed only by the button area disappearing; `<section role="region" aria-label="Actions">` provides landmark navigation; `role="group"` with `aria-describedby` links the button cluster to the turn-summary line. The spinner-targeting fix (#500) introduces `pendingActionType` as an explicit prop rather than always targeting `validActions[0]` — critical before M6 adds multiple simultaneous action types where the wrong button would spin. The identity-fetch fix (#496) replaces the bare `.catch(() => {})` with a handler that sets an `identityError` ref and renders an error banner; the console log gives operators visibility while the banner gives players feedback instead of a silently null player side.

Phase 2 replaces the client-side `validActionsForState` stub (#495). The M5 stub always returned `[END_PHASE]`, which would silently diverge from the server's `getValidActions` once M6 adds `ROLL_INITIATIVE`, `ACTIVATE_STACK`, and other action types. The fix adds `GET /api/v1/games/:id/actions` to the server (session-authenticated, sources player side from session not body), and `GameView.vue` calls it after initial load and after each `game:state-updated` socket event. The computed `validActions` in the view was trimmed to simply gate on `activePlayer === localPlayerSide` and return `serverValidActions.value` — the server is now the single source of truth for what actions are legal.

Phase 4 extracted `serverStripNonPlayableBoundaryEdges` from the `mapEditor.js` route module into `server/src/engine/edge-strip.js` (#492). The function had been correctly commented as "should live in engine/" since it imports from `engine/hex.js` and implements playability-boundary geometry, not HTTP routing. The new module returns a strip count (useful for the save-time announcement), has its own 13-test suite covering faces 0/1/2 with odd/even column parity, empty-edges starting variants, and multi-face count returns. The `mapEditor.js` route now imports the function and passes it as a `transform` hook to `editorRouteFactory`. Issues #467 (edge-model test expansion) and #481 (UnitStatsPanel 3-unit paging, games.test.js saveGame contract) added the missing test cases; #468 and #470 were confirmed already implemented in the prior sprint and closed. The debt register ends at 10 open items / score 16 — the achievable floor without closing M6-blocked items (#379 will close naturally during M6 engine work).

## 17:03 — PR: M5 UI Completion — ActionPanel, Socket Wiring, Store Submission Pipeline

This PR delivers the three follow-up M5 UI tickets (#472, #473, #474) that were formally designed in `docs/designs/m5-game-ui-detail.md` but left unimplemented when M5 was declared complete. The work completes the game interaction loop: a player can now see the current turn/phase/step, see what actions are available, submit them through the UI, and receive live state updates via Socket.io — all without touching the browser console. The HLD M5 status block is updated to accurately describe what is delivered.

The three additions are each independently layered. Phase 1 extends `useGameStore` with `pendingAction` (a ref that holds `{ type, payload }` during the in-flight POST), `submitAction` (issues the POST to `/api/v1/games/:id/actions` with `expectedVersion` from the current `gameState.version`, updates `gameState` on success, sets `error` on 422/409/500), and `refreshGame` (a thin wrapper over `loadGame` that returns its promise so callers can `await` it). The generation guard from the original `loadGame` implementation is reused — `refreshGame` riding the same codepath means socket-triggered refreshes are automatically superseded by newer loads. Phase 2 creates `ActionPanel.vue` as a purely presentational component: it renders "Turn N — [phase] ([step])", one button per `validActions` entry with a title-cased label, a spinner overlay on the first active button while `pending` is true, and a "Waiting for [side]…" message when `activePlayer !== localPlayerSide`. The component has no store access — all data flows in via props and the only output is a `submit-action` emit.

Phase 3 wires `GameView.vue` to the socket and renders `ActionPanel` in the sidebar. Socket setup is deliberately kept in `GameView`, not the store — the store is designed to be server-unaware. On mount, a `socket.io-client` socket is created, `game:join` is emitted with the current `gameId`, and a `game:state-updated` listener calls `gameStore.refreshGame`. On unmount, `game:leave` is emitted with the captured `_mountedGameId` (not `route.params.id` — the route params are gone by the time `onUnmounted` fires in the test environment) and the socket is disconnected. `localPlayerSide` is sourced from `GET /api/v1/games/me`, which returns `{ gameId, side }` from the session — this is the authoritative server-sourced identity, matching how the server validates actions. For M5, `validActionsForState` is a trivially simple pure function that always returns `[{ type: 'END_PHASE', payload: null }]` when a phase and step are present; the real per-phase derivation logic is deferred to M6 when per-stack activation granularity makes client-side derivation complex enough to warrant a dedicated `GET /valid-actions` endpoint.

All three phases were implemented TDD — tests were written first to confirm the red phase, then implementation added to make them green. The test suite grew by 47 tests: 7 for `submitAction` paths (success, 422, 500, 409, pendingAction lifecycle), 1 for `refreshGame`, 8 for `ActionPanel` rendering and emit behavior, and 9 new `GameView` integration tests covering socket join/leave/listener, `refreshGame` callback, `ActionPanel` rendering, pending prop passthrough, and `submitAction` routing. The full `quality:strict` gate (validate-data, lint, format:check, 2429 tests, build) passes cleanly with no new debt introduced.
