## 11:53 — PR: PR #649 team-review fixes — Discord notifications security and test hardening

This PR applies all findings from the two-phase team-review of PR #649 (M8 Discord webhook notifications). The primary review produced nine findings, all fixed in place. A second-pass review was triggered because the fix diff touched `requireSide.js` (auth middleware) and the action route — high-risk surfaces per the project's quality rails. The second pass added six more findings, two of which were fixed in place and four deferred as scored issues.

The most structurally significant fix is the `isAllowedDiscordWebhook` extraction and export. Previously the Discord-domain SSRF allowlist existed in two independent places: as an inline hostname chain in the game-create route and as a new `Set`-based helper inside `discord.js`. Keeping two copies of a security policy is fragile — a hostname added to one but not the other would let a URL pass creation-time validation but be silently dropped (or accepted) at send time. The fix exports `isAllowedDiscordWebhook` from `discord.js` and has the create route call it directly, making `discord.js` the single source of truth.

The `req.game` projection fix in `requireSide` is a defence-in-depth hardening. The middleware already loaded the game row to validate the session token; attaching the whole row to `req` for downstream use made sense to eliminate a redundant `getGame` call, but the raw row carries `side_a_token` and `side_b_token`. Rather than document "don't serialize this", the fix projects to `{ id, status, discord_webhook }` before attaching, making accidental credential leakage structurally impossible regardless of what future handlers do with `req.game`.

Other fixes: import ordering in `games.js` (notifications → store alphabetically); misleading test name renamed; `buildActionPayload` undefined-turn branch exercised; VP round-trip test tightened from `toBeGreaterThanOrEqual(4)` to `toBe(4)`; `allowed_mentions: { parse: [] }` added to suppress `@everyone`/`@here` injection; `DISCORD_WEBHOOK_TEST_URL` gated behind `NODE_ENV !== 'production'` to prevent staging leakage; route integration tests added covering the three webhook paths (called when configured, skipped when null, response succeeds when webhook rejects). Four low-score documentation and test-coverage items were deferred as issues #654–#657, all scored 1–2 and assigned to M8.

## 18:26 — PR: feat(infra): Terraform IaC for DigitalOcean provisioning (#659)

This PR replaces the manual Phase 3 provisioning steps from the `m8-notifications_20260622` track with a declarative Terraform configuration in `infra/`. Before this PR, standing up a new production environment required manually creating a DigitalOcean Droplet, configuring nginx and PM2, creating a Spaces bucket, and wiring three GitHub Actions secrets — all from the console. A machine switch or accidental Droplet termination meant repeating all those steps from memory. The new config reduces that to `terraform init && terraform apply` followed by populating `.env` once over SSH.

The most structurally important design decision was **separating the Terraform state bucket from the application game-state bucket**. The initial implementation (caught by the architecture and maintainability reviewers) pointed the S3 backend at `lob-online-games` — the same bucket that Terraform also managed as a resource. This created a fatal circular dependency: `terraform destroy` would delete its own state file mid-operation, and `terraform apply` on a fresh machine would fail with a 409 because the bucket already existed from the manual bootstrap step. The fix uses a dedicated, unmanaged `lob-online-tfstate` bucket for state (created once manually, never touched by Terraform) and keeps `lob-online-games` as a fully managed app resource with `prevent_destroy = true` and versioning enabled.

The cloud-init bootstrap underwent substantial revision during the review cycle. The original draft used an unverified `curl | bash` NodeSource install, started PM2 before the operator had populated any real secrets (causing an immediate crash-loop against `CHANGE_ME` placeholders), and used the wrong env var names (`SESSION_SECRET` instead of `JWT_SECRET`, `DB_PATH` instead of `SQLITE_PATH`) that don't match what the app actually reads. The revised version switches to a GPG-key-verified apt repo for Node 20, wraps all runcmd steps in a single `set -euo pipefail` script piped to `/var/log/bootstrap.log` so failures surface visibly, creates an unprivileged `lob` service user instead of running as root, and deliberately does **not** start the app — that step is deferred to Step 7 in PROVISIONING.md so the operator can populate `.env` first with the correct variable names.

Several security findings were fixed in-place: the port 3000 inbound firewall rule was removed (nginx proxies from 127.0.0.1; the app should not be reachable directly), provider version pins were tightened from unbounded `>= 2.0` to pessimistic `~> 2.0`, and the `DO_SSH_USER` GitHub Actions secret was promoted from a hardcoded `"root"` literal to `var.ssh_user` (defaulting to the new `lob` service user) so day-2 hardening is a single variable change. Three remaining security concerns — SSH open to `0.0.0.0/0`, no TLS, and the SSH private key passing through Terraform state — were explicitly documented in the Security Notes section of PROVISIONING.md rather than deferred as issues, since they are inherent constraints of the chosen architecture at this stage of the project and not fixable without broader scope changes.

All 13 review findings were fixed in place; zero findings were deferred as tech-debt issues. The `/team-review` second-pass trigger was not required since all fixes were limited to infra config and documentation — no app code, auth surfaces, persistence paths, or rules-engine logic was touched.
