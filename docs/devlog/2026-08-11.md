## 21:56 — PR: Documentation, Data-Metadata, and Issue-Tracker Sync

While reviewing South Mountain's data-file completeness (map.json, oob.json, leaders.json),
we found that terrain digitization — completed in M9 by PR #684 (closing #669) — had never
been reflected outside the code. `map.json`'s own internal `_description`/`_digitizationNote`
fields, `docs/library.md`, `docs/library.json`, `docs/agents/domain-expert/design.md`, and the
HLD risk register all still described the pre-completion "scaffold, 31 known hexes, digitization
in progress" state, even though the file itself has held 841/841 typed hexes with zero `unknown`
since late June. A dead `_todoHexes` block (setup-position zones that were already resolved in
`scenario.json`) and an obsolete `_digitizationPlan` block were removed from `map.json` at the
same time. `_status` stays `"partial"` rather than flipping to `"available"`, because hexside
features — roads, streams, stone walls, fords — are genuinely still undigitized; that follow-up
work is correctly tracked in open issue #685, so this PR only fixes the surrounding prose, not
the underlying gap.

The same investigation turned up a Conductor track-record inconsistency: track
`m9-map-completion_20260625` was registered `[ ]` in `tracks.md` despite its own
`metadata.json`/`plan.md` already saying `complete`. That one was a clean fix — both files
live on `master`, so bringing `tracks.md` in line with them was unambiguous.

`m9-discord-oauth_20260625` looked like the same kind of drift at first — its `metadata.json`
read `"pending"` with `0/3` phases while a `plan.md` showed every task checked and "Completed
2026-06-28" — but that fully-checked `plan.md` only exists on the separate, unmerged
`feat/m9-discord-oauth` branch. An initial fix set `metadata.json` to `"complete"` by reading
`plan.md` off that branch's working tree, which produced a _new_ same-directory inconsistency
once landed on this branch: `metadata.json` claiming `complete` next to a `plan.md` (the one
actually on `master`) still reading `[ ] Not Started`. `/code-review` on the resulting PR caught
it. The corrected fix keeps `metadata.json` matching the `plan.md` that actually exists in this
tree — `"pending"`, `0/3`, `0/10` — with a note that the real completion lives on the unmerged
branch and this file should only flip once that branch is PR'd and merged.
