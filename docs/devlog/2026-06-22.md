# 2026-06-22

## 10:05 — PR: M8 Local Dev Infrastructure — MinIO + Discord Sink

M8 replaces the current local-file game-persistence layer with DigitalOcean Spaces (S3-compatible
object storage) and adds Discord webhook notifications for game events. Before any of that code can
be written, local development needs drop-in substitutes for both external services. This PR delivers
exactly that: a Docker Compose file that runs MinIO as a local S3 emulator, and a lightweight
Express sink script that captures and logs Discord webhook calls.

The MinIO service runs via `docker compose up -d` and exposes the S3 API on port 9000 and the
admin console on port 9001, both bound to `127.0.0.1` so they are only reachable from the local
machine. Credentials default to `minioadmin:minioadmin` — intentionally weak dev defaults with no
production exposure. The `.env.example` was updated to use a provider-neutral `SPACES_*` naming
scheme (replacing the previous `DO_SPACES_*` names) so the same env-var contract works for both
MinIO locally and DigitalOcean Spaces in production. `SPACES_FORCE_PATH_STYLE=true` is documented
as required for MinIO's path-style addressing.

The Discord webhook sink (`npm run discord:sink`) is a 17-line Express server that listens on
`127.0.0.1:4040`, returns 204 for every POST, and pretty-prints the request body to stdout. It
requires no build step, no auth, and no configuration beyond `DISCORD_WEBHOOK_TEST_URL=http://localhost:4040`
in `.env`. Express is resolved through the npm workspace — the server workspace already declares
`express ^4.22.2`, which hoists to root `node_modules`. To make this dependency contract explicit
rather than relying on non-deterministic hoisting, `express ^4.22.2` was added to the root
`devDependencies` as part of the team-review fixes.

The team review caught two security findings: both MinIO and the Discord sink were initially
binding to `0.0.0.0`, exposing them on the LAN with default credentials. Both were fixed to
bind to `127.0.0.1`. A body-size limit (`64kb`) was also added to the sink's JSON parser as a
cheap hardening step. CLAUDE.md was updated with a new "Local Infrastructure (M8)" section
documenting `docker compose up`, the `lob-online-dev` bucket creation step, and `npm run discord:sink`,
since these are new hard dependencies for M8 development work that wouldn't otherwise be discoverable.

Several items were intentionally deferred to the M8 persistence track: auto-bucket creation via
an `minio/mc` init container (fits naturally alongside the S3 client code), a `SPACES_REGION` env
var (the right value depends on how the AWS SDK client is configured), and a Docker healthcheck
(needed once the init container exists). The `DISCORD_WEBHOOK_TEST_URL` naming and the
app/listener separation in the sink script were noted as low-priority cleanup items but do not
block M8 development.

## 12:49 — PR: M8 Persistence + Auth Hardening — Spaces Store, SQLite Migration, Faction Binding

This PR delivers the persistence layer for M8 multiplayer: game state is now stored in DigitalOcean
Spaces (S3-compatible object storage) rather than the local filesystem, the SQLite games table is
migrated to carry faction and Discord webhook columns, and a new `requireSide` middleware enforces
token-level authorization on all game action routes.

The persistence split is deliberate: SQLite holds the metadata needed for lobby listing and
authentication (game id, side tokens, status, faction, webhook), while Spaces holds the full
`GameState` JSON blob and an append-only history log keyed by zero-padded sequence number. This
two-store design lets the metadata layer stay synchronous and queryable without pulling multi-KB
game state for every lobby operation. The `store/index.js` barrel re-exports from both stores so
the rest of the codebase sees a single surface. `saveGame` implements optimistic concurrency via a
read-compare-write cycle: before writing, it fetches the current object and compares versions,
throwing on mismatch. This is best-effort (not a true atomic CAS) but catches the common case of
stale-client overwrites; a true S3 ETag-based conditional write is noted as a follow-on improvement.

The SQLite migration from schema v0 to v1 adds `side_a_faction`, `side_b_faction`, and
`discord_webhook` columns and is gated by `PRAGMA user_version` so it is safe to re-run on every
restart. For fresh databases the `CREATE TABLE IF NOT EXISTS` in `SCHEMA_V1` already includes the
new columns; for pre-v1 databases the three `ALTER TABLE ADD COLUMN` statements do the upgrade,
guarded by `PRAGMA table_info` column presence checks since SQLite will error (not no-op) on a
duplicate ADD COLUMN. The `joinGame` route enforces faction binding: once a player joins as union or
confederate, their session is bound to that side and re-join requests for the opposite side are
rejected with 403. The `discordWebhook` field is optional and validated as an http/https URL before
being persisted.

The new `requireSide` middleware consolidates all authentication logic that was previously spread
across individual route handlers: it checks that a player session exists (401), that the session
`gameId` matches the route `:id` (403), that the game row exists in SQLite (404), that the game is
active (409), and finally that the session's `sideToken` matches one of the stored side tokens
(403). This ordering intentionally returns 409 before the token check — a holder of a correct
`gameId` but stale token learns the game's lifecycle state. This is a documented, scoped
information-disclosure tradeoff: the prior 403 gate already proves the caller was in this game.

The team review surfaced several items deferred to follow-on work: the unauthenticated `DELETE`
route, the non-atomic S3 version check, uncompensated dual-store create/delete, the split
`GameNotFoundError` class identity, and missing test coverage for the `version: undefined` opt-out
path and faction validation. These are filed as GitHub issues and scored in the accompanying
tech-debt report.

## 17:49 — PR: M8 Discord Notifications + Hex Control Wiring

This PR adds the two remaining M8 code deliverables: Discord webhook notifications on each game action, and verification that the hex-control VP wiring infrastructure is complete and tested. The notification system is deliberately fire-and-forget — `notifyWebhook` is called without `await` after `saveGame` so webhook latency or failures never block the game action response. The `DISCORD_WEBHOOK_TEST_URL` environment variable allows local development and CI to route calls to the Discord sink started by `npm run discord:sink` instead of a live Discord channel.

The `buildActionPayload` function produces a minimal content string (game ID, action type, active side, turn number) rather than an embed. Discord embeds were considered but ruled out for MVP — the content string is sufficient for PBEM notifications and embeds can be added later without changing the calling contract. Error swallowing is total: both network failures and non-2xx responses are caught and logged with `console.warn`, never re-thrown. This matches the design intent: a broken webhook must never interrupt a game in progress.

Phase 2 (hex control VP wiring) turned out to be partially complete from M7. `updateHexControl`, the `hexControl` field in `GameStateSchema`, and the `initGameState` initialization were all already in place. The missing piece was a round-trip integration test confirming that `updateHexControl` output flows correctly into `computeVP` — that test was added. The actual MOVE action wiring (Task 2.2) remains blocked by issue #634: no MOVE action handler exists yet, so there is no call site to wire into. The functions are ready and the deferred issue tracks the wiring.

One infrastructure fix was required: the ESLint `n` plugin was flagging `fetch` as unsupported because the project lacked an `engines` field in `package.json` and the plugin's built-in data incorrectly marks `fetch` as requiring Node 21 (it has been stable since Node 18). Fixed by adding `"engines": {"node": ">=20.0.0"}` to `package.json` and explicitly setting `version: '>=20.0.0'` with `fetch` in the `ignores` list in `eslint.config.js`. This is a one-time config fix that benefits all future uses of Node 18+ globals.

Phase 3 (DigitalOcean Droplet provisioning) is a manual task requiring a DO account and is tracked separately. The code is fully ready to serve production once the Droplet, Spaces bucket, and three GitHub secrets (`DO_DROPLET_IP`, `DO_SSH_USER`, `DO_SSH_KEY`) are in place.
