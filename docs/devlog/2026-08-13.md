## 02:16 — PR: Map Data Debt Sprint — Issues #693-696

This PR closes the four tracked-debt items `/team-review` surfaced on PR #692
(map-col64-investigation_20260812): a missing regression test for
`gridSpec.cols`, a non-blocking `validate-data.js` check with no test
coverage of its own, an undocumented and unenforced `playable` schema field,
and South Mountain map-status facts duplicated by hand across multiple
documentation locations. All four were low-to-moderate score items (2 each,
8 total) filed under the project's Immediate Debt-Capture Policy rather than
folded into #692 itself, which was correctly scoped narrowly to the
`gridSpec.cols` config fix.

The `#693` fix (`server/src/engine/map.test.js`) turned into the most
interesting phase: the first invariant drafted — every recorded hex falls
within `[1, cols] x [1, rows]` — was itself wrong. The real map data records
boundary-marker hexes at row 0 and row 36 (`playable: false`), one row
outside the declared `gridSpec.rows: 35`, matching the same north/south-edge
convention `map-col64-investigation_20260812` considered (and rejected) for
column 64. The test was corrected to allow that documented exception rather
than asserting a stricter invariant than the data actually follows.
Mutation-testing (temporarily reverting `gridSpec.cols` to 64 in a scratch
copy) confirmed the new test catches the exact #691 regression class.
Investigating #693 also surfaced a second, more concrete instance of the
same risk the issue described: `client/src/utils/calibration.js`'s
`DEFAULT_CALIBRATION.cols` was still `64` — a live write path, since the Map
Editor seeds calibration from `localStorage` before any server load. Fixed
inline after checking with the user, since it was a one-line, low-risk
change directly tied to the issue's stated root cause. Fixing it also
surfaced that `useCalibration.test.js` had its own hand-copied duplicate of
`DEFAULT_CALIBRATION` — exactly the drift class this whole track exists to
guard against — replaced with a real import.

`#694`'s fix promoted `validate-data.js`'s grid-coverage check from `warn()`
to `fail()`: a coverage gap silently opens phantom grid cells to the
pathfinder, since `hex.js` gates reachability purely on `gridSpec` bounds, so
this was a correctness hazard rather than a cosmetic one. The three checker
functions in scope (`checkSetupHexesInMap`, the new `checkGridCoverage`, and
`checkEdgeFeatureTypesRegistry`) were extracted to named exports, and the
script's main execution was guarded behind an `import.meta.url ===
process.argv[1]` direct-run check so `scripts/validate-data.test.js` can
import them for testing against small in-memory fixtures without triggering
a full run (real file loads, `process.exit`) as a module side effect.

`#695` added a scope comment to the schema's `playable` field (matching the
`ELEVATION_TYPES` export comment style) plus a characterization test in
`movement.test.js` pinning that the field is not consulted by the
movement/pathfinding engine — a deliberate documentation choice, not a
silent gap. Actually enforcing `playable: false` as impassable terrain
remains explicitly out of scope, since that's a rules-behavior change
requiring domain-expert sign-off, not a debt-cleanup fix.

`#696` added `scripts/library-sync.test.js`, asserting `docs/library.json`'s
`SM_MAP_DATA.hexCount` and `status` fields stay in sync with
`data/modules/south-mountain/map.json`'s real `hexes.length` and `_status`,
so a future map edit that forgets to update `library.json` fails CI instead
of silently going stale. Per the approved spec, only two of the seven
duplication locations were trimmed to point at `docs/library.md` instead of
independently restating counts — `high-level-design.md`'s risk-register row
and `domain-expert/design.md`'s `SM_MAP_DATA` row — leaving `docs/library.md`
itself as the intended human-readable source of truth, plus `CLAUDE.md` and
HLD's other two mentions untouched as agreed out-of-scope.

The full quality suite (`validate-data`, `lint`, `format:check`, `test` —
160 files / 3277 tests, `build`) is green throughout, with one pre-existing

## 12:30 — PR: M9 Discord OAuth — Identity Layer

Picked up `feat/m9-discord-oauth` (#668, #410) — implemented in June across
three Checkpointed phases but never merged. Merged 7 weeks of intervening
master history into the branch (resolving conflicts in CLAUDE.md,
conductor/tracks.md, HLD, and devlog.md — all clean, no content loss), then
smoke-tested the auth flow live against a real server, SQLite DB, and MinIO
before touching review. That smoke test caught a real bug immediately:
creating or joining a game silently logged the user out of their Discord
session, because `req.session.regenerate()` (a pre-existing session-fixation
defense) wipes passport's serialized identity, and nothing re-called
`req.login()` afterward. Fixed and mutation-verified across all three call
sites before review even started.

A full 4-dimension `/team-review` (security, architecture, testing,
maintainability) then found substantially more than the earlier map-data
PR: 7 High-severity findings, several cross-confirmed by 2-3 reviewers
independently and verified against actual `node_modules` source and real
coverage numbers rather than taken at face value. Two were genuine security
vulnerabilities — the Discord OAuth handshake had no `state` parameter
(passport-oauth2's default `NullStore.verify()` unconditionally returns
`true`, meaning zero CSRF protection on the login flow), and `.env.example`
was shipping `AUTH_DEV_MODE=true` as the default, a mistake introduced
earlier in this same branch pickup. Combined with a third finding — the
`dev-` synthetic-user bypass in `deserializeUser` had no runtime check of
the flag at all, so a session minted while it was on kept authenticating
for its full 14-day lifetime after being turned off — these three together
were a real auth-bypass footgun on first deploy.

Given the volume and severity, the user was asked how to scope the fix
pass rather than proceeding unilaterally: fix all Highs plus security-
flavored Mediums now, defer the rest as tracked debt (#698-700). Beyond
the security fixes, this surfaced a genuine functional bug worth fixing
regardless of "security" framing: identity was recorded
(`side_a_user_id`/`side_b_user_id`) but never checked for authorization,
and logging out mid-game permanently locked the owner out of their own
game (409 "Side already taken" on any rejoin attempt) — a real scenario
for a correspondence wargame played over many days. Added an
identity-based reclaim path (reissue a token when the DB still records
this logged-in user as the owner) rather than just closing the read-side
gap, plus a DELETE `/:id` ownership check using data this branch already
added.

The most valuable test added was a real integration suite
(`games.auth-integration.test.js`) wiring genuine `express-session` +
`passport.initialize()`/`session()` + an in-memory SQLite DB + the real
routers, driven through a cookie-persisting `supertest` agent — the kind
of test that would have caught the original regenerate-drops-login bug
directly, since the existing unit tests' mocked `req.login` stub
structurally could not have. Also caught and fixed mid-fix: the earlier
`ff2c86d` regression test asserted that `req.login` was _called_ but not
in what _order_ relative to `regenerate` — mutation-testing confirmed
swapping the order still passed all 92 tests, which would have silently
reintroduced the original bug under a different shape.

Full quality suite green throughout (168 files / 3365 tests). Live
re-verified end-to-end after all fixes: login → create → logout →
re-login → reclaim → still-logged-in, plus confirmed a second identity
cannot hijack an already-owned side (409, not a silent reclaim).

## 16:51 — PR: Engine Debt Sprint — Issues #676-679, #681

Closed the oldest open debt in the register — five items filed against
PR #674's `/team-review` six weeks ago (#676 loadOob N+1 disk reads, #677
duplicated formation-classification ladder, #678 SM §5.1 VP hex control,
#679 column formation, #681 duplicated IIFE helper). Two of the five
(#678, #679) weren't pure code cleanup — they were missing/incorrect
rules mechanics — so `domain-expert` was consulted before any
implementation began, per this project's convention.

The ruling reshaped both. For #678, it confirmed the issue's premise (SM
§5.1: control transfers for hexes "occupied or moved through," not just
the destination) but added a load-bearing nuance the issue missed:
unlimbered artillery can never satisfy "moved through," since LOB §3.6a
says unlimbered artillery cannot move at all — only limbered artillery
moves, and limbered artillery isn't VP-eligible. That meant the fix
needed no artillery special-casing beyond what `isVpControlEligible`
already did — walking the submitted path and calling `updateHexControl`
for every non-start hex was sufficient. Scoped to the MOVE action only;
the same textual gap in retreat/charge-advance/Skedaddle traversal was
explicitly descoped and filed as #703. For #679, the ruling found the
issue significantly undersold scope: LOB v2.0 bars Column-formation
infantry from firing entirely, from being Charge attackers, and applies a
severe Rear-facing combat/morale penalty — a movement-only
implementation (as filed) would have left the engine in a _worse_,
rules-inconsistent state than the current gap, not just an incomplete
one. Closed #679 without implementing it; filed #704 as a properly-scoped
feature issue (movement + combat + morale together) for its own future
track, explicitly not labeled `tech-debt` since it's new functionality.

A full 5-dimension `/team-review` (security, architecture, testing,
maintainability, domain — domain added given this touches rules-engine
logic) followed. Security and domain came back clean; the other three
converged on a real, independently-confirmed correctness bug: the new
`resolveFormationKey` (extracted for #677) misclassified artillery as
infantry whenever `unit.formation` was unset — which is every battery's
state at game setup, since `init.js` never initializes it — or when the
OOB record had no `type` field, true for every real South Mountain
battery (they carry `gunType`, not `type`). Combined with #678's own
path-walk change in the same branch, this would have let a
should-be-immobile artillery unit illegally move using infantry costs and
claim every VP hex along that illegal path, not just one. Fixed by
checking `gunType` and applying the `unit.formation ?? 'unlimbered'`
default already used at every other artillery call site in the codebase
— catching one self-inflicted regression along the way, where an early
version of the fix broke degraded-mode (no-OOB) unlimbered-artillery
detection by gating `unit.formation` behind an OOB-derived check instead
of trusting it directly.

The review also caught three vacuous-under-mutation tests (an
error-code-only assertion that couldn't distinguish the real guard from
an unrelated fallthrough; a call-count spy that never confirmed the loop
it protected was actually reached; artillery fixtures shaped nothing like
real data) and an architecture gap of its own making: `getValidActions`
now avoided _repeated_ OOB reads within one call but still ignored
`ctx.oob` entirely, silently re-reading from disk even when the caller
already held a validated copy — closed by threading `ctx` through, the
one remaining holdout from the `ctx.oob ?? loadOob()` seam already used
everywhere else in the engine. Per this project's rule that debt-cleanup
PRs must not generate new deferred debt, every finding was fixed in place
in the same PR rather than filed as a follow-up — including reconciling
the track's own conductor docs, which had drifted from actual state in
the same recurring way this project has been bitten by before (spec.md
still Draft, plan.md prematurely marked Complete, task counts stale).

Full quality suite green throughout (169 files / 3387 tests, zero
unexpected warnings). Every new or strengthened regression test was
mutation-verified against its target fix before being considered done.

## 17:15 — PR #705 opened; second-pass review catches a real bug the fix itself introduced

PR #705 opened for the engine debt sprint. Because the Phase 6 review-fix
diff touched rules-engine paths (formation resolution, `getValidActions`'s
dispatch hot path), the project's quality rails require a targeted
second-pass review before closeout — not a formality here. A
`domain-expert` pass confirmed the artillery-classification fix itself is
rules-accurate (Unlimbered-by-default matches LOB §3.6a; the `gunType`
discriminator has zero false positives against the real SM OOB). A
correctness/maintainability pass mutation-verified all of Phase 6's claims
independently and then found something neither the original five-dimension
review nor my own verification had: correctly classifying unset-formation
batteries as Unlimbered (0 MP, since Unlimbered cannot move) left
`handleLimber` with nothing to restore `remainingMPs` from — it only ever
flipped `unit.formation`, never touched MPs. Every real battery in every
game would have been permanently unable to limber-then-move in one
activation; the previous (buggy) classification had accidentally masked
this by handing unset-formation batteries a nonzero, if wrong, MP pool.

A second domain-expert consultation pinned the exact mechanic: LOB §3.6a
("must change to Limbered formation first, costing 3 MPs, and then move
using its remaining MA") means the 3 MP formation-change fee comes out of
the Limbered allowance itself (7, in this scenario), not a separate cost
stacked on top of the Unlimbered 0 MP the unit was correctly initialized
with. Fixed `handleLimber` to grant `remainingMPs = movementAllowances
.limbered - 3` on success, verified end-to-end against the real South
Mountain OOB and scenario data (0 MP → LIMBER → 4 MP), and mutation-tested.
The symmetric gap — `handleUnlimber` never deducting the same 3 MP cost —
was investigated and found to be a different kind of issue: it was already
reachable before this branch (a battery starting an activation already
Limbered was already correctly initialized with nonzero MPs, independent
of the classification fix), so it isn't a regression this PR introduced.
Filed as #706 rather than fixed in place, consistent with the project's
distinction between "caused by this PR" and "pre-existing, discovered
incidentally."

Also fixed three LOW findings from the same second-pass pass: a vacuous
`e.code`-only assertion in `move.test.js` that mirrored the exact pattern
Phase 6 had already fixed elsewhere in the same file, an orphaned comment
left behind by a describe-block split, and a dropped
formation-vs-conflicting-oobUnit precedence test case. Full suite green
throughout (169 files / 3390 tests).
