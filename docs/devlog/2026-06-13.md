## 08:44 — PR: Pre-M6 Debt Sprint — Score 3+ and Low-Hanging Fruit

This PR completes a pre-M6 housekeeping sprint targeting all open debt items scored 3 or higher plus a selection of easy score 1–2 items. The net open debt score drops from 41 to 31 — not yet below 15, but all the high-risk structural items are resolved before combat, morale, and orders work begins in M6.

The highest-priority fix was #540: `moduleData.js` PUT/POST/DELETE routes were mounted unconditionally, meaning any origin that passed the CSRF check could overwrite data files at `/api/v1/modules/:slug/*`. The fix adds a middleware guard at the top of the router that returns 404 for non-GET requests when `MAP_EDITOR_ENABLED` is not `'true'` — identical to the guard already used for other editor routes in `server.js`. All existing PUT tests were updated to set the flag; two new guard tests confirm the behavior in both directions.

Issue #541 addressed a silent correctness hazard in `useOobPersistence`: when called without a `moduleSlug`, the composable fell back to legacy `/api/tools/*` URLs without any indication that it was doing so. Push operations would silently write to the wrong endpoints. The fix adds a `console.warn` in `buildUrls` so the fallback is no longer invisible. Full removal of the legacy path was not done because `useOobStore` still calls `loadData()` (no slug) as a standalone fallback when the route has no `moduleSlug` param. That codepath remains valid for the legacy tool entry point. The warning makes misdirected writes detectable without breaking existing behavior.

For #531, `MINUTES_PER_CONDITION` lived only in `ScenarioEditorView.vue` while `engine/init.js` hardcoded `15` with a comment noting the limitation. Extracting to a shared module was complicated by the client/server split: Vite's security model blocks imports from outside the client root, so a single shared file isn't feasible. Instead, two sister files were created — `server/src/engine/turnTime.js` and `client/src/config/turnTime.js` — both exporting identical constants with a cross-reference comment. The `?? 15` fallbacks in the view were replaced with `?? MINUTES_PER_CONDITION_DEFAULT`, also exported from the config.

The Phase 3 low-hanging-fruit work added `VISIBILITY_UNLIMITED = 999` to eliminate the magic sentinel value; an upper-bound refine on `visibilityHexes` (1–20 or 999); a `.superRefine` uniqueness check on `lightingSchedule` `startTurn` values; and five new test cases covering `totalTurns` edge cases (empty schedule, inverted time range, missing `firstTurn`) and the `lightingStartTimes` night-turn clock accumulation. Direct URL construction tests were also added for both `useMapPersistence` and `useOobPersistence`. Issue #533 (removing `totalTurns` from `scenario.json`) was deferred: the field is required in the Zod schema and present in all nine module data files, making it a schema migration rather than a simple cleanup.

## 12:46 — PR: Turn Loop Core — Concrete Valid-Action Candidates and ActionPanel Labels

This PR closes three M5.5 turn-loop-cleanup issues: #550 (engine concrete candidates), #551 (ActionPanel payload labels), and #552 (store ownership of valid actions — already implemented). The theme is making the action pipeline data-driven from the engine outward: instead of the engine returning broad type strings, it now returns one concrete candidate per legal action with the full payload attached, so the client can render and submit actions without manually constructing payloads.

The central change is in `getValidActions` in `server/src/engine/actions/index.js`. Three action types now carry real payloads. `ACTIVATE_STACK` returns one candidate per occupied, un-activated on-board hex (`{ hex }`) — already-activated and off-board units are excluded, and stacks at the same hex are deduplicated. `ISSUE_ORDER` returns two candidates per pending issuance — one for `attack` and one for `move` — each carrying `{ unitId, orderType }`. `ROLL_INITIATIVE` returns one candidate per eligible leader×unit pair (`{ leaderId, unitId }`) when `leaderState` has entries, and falls back to a single `null`-payload candidate for the M5 steel-thread path where no leaders are tracked. `END_PHASE` and `END_ACTIVATION` continue to carry `null` payloads. `dispatch` was unaffected because it checks `validActions.some((a) => a.type === type)`, so multiple candidates of the same type still gate correctly.

The ActionPanel needed one label fix to handle the two-candidate `ISSUE_ORDER` case. Before this PR, `toTitleCase('ISSUE_ORDER')` rendered "Issue Order" for both attack and move buttons — indistinguishable. The new `actionLabel()` function special-cases `ISSUE_ORDER` to append the order type: "Issue Order — Attack" and "Issue Order — Move". All other action types continue to use the existing title-case transform. The payload pass-through from engine → store → ActionPanel → `submitAction` was already correct and required no wiring changes.

The store half of the story (#552) was completed in a prior debt sprint and verified during investigation — `useGameStore` already owns `serverValidActions` with a generation guard (`_actionsGeneration`), and `GameView` already consumes from the store rather than local state. The track plan records this as a pre-implemented task to document the outcome accurately.

A non-obvious constraint: `ACTIVATE_STACK` now returns a variable-length list of candidates rather than a single entry. The `dispatch` gate (`validActions.some(a => a.type === type)`) still accepts any `ACTIVATE_STACK` submission regardless of which hex was in the specific candidate — the handler validates the hex further. This means the engine's candidate list is informational for the UI (what hexes can be activated?) but not a payload whitelist. Future combat targeting will need to decide whether to follow the same informational pattern or add per-candidate payload validation to `dispatch`. That design question is deferred to M6.

## 16:25 — PR: Lobby and Auth Cleanup — Side Entry Flow and Session Guard (#549 #553)

This PR delivers two small but important correctness fixes to the M5 session foundation before M6 combat work begins. The changes are independent but both touch session semantics, so they land together in one PR rather than two separate branches.

The first fix (#553) tightens the HTTP status code returned by `requireSide` when a request arrives with a session for the wrong game. Previously both "no session" and "session for a different game" returned 401. The distinction matters: 401 means "prove who you are," while 403 means "we know who you are, but you don't own this resource." A game client holding a stale session for game A that accidentally polls game B should get 403, not 401, so it can distinguish a network routing error from a genuine auth failure without silently re-prompting. The fix splits the single compound guard in `requireSide` into two separate checks. Nine new route-level tests cover all three guarded routes (`GET /:id`, `GET /:id/actions`, `POST /:id/actions`) × all three session states (same-game, different-game, missing). Three existing tests that previously asserted 401 for the different-game case were updated to 403.

The second fix (#549) corrects two bugs in the lobby flow. First, `POST /api/v1/games` was assigning the creator to the Confederate side — a one-line holdover from the initial scaffolding that had no rule basis. In LOB v2.0 the Union player traditionally moves first and was implicitly assumed to be the game creator; correcting this to `side: "union"` aligns the code with that assumption. Second, the USA and CSA side-entry buttons in `LobbyView` were disabled whenever `game.status !== 'open'`, which meant no player could enter an active game from the lobby. The `:disabled` binding was removed entirely — the server's `joinGame` route already enforces all the relevant game-state constraints, so the UI disablement was redundant and actively harmful. The `joinGame` store flow required no changes; it already posts to `/api/v1/games/:id/join` with the selected side, which works for both open and active games.

No new debt was accepted. The lobby side-entry and session guard changes are each contained within their existing file boundaries, with no new abstractions or shared modules added. Full production auth hardening (issue #410) remains explicitly out of scope and is tracked separately. The `npm run quality:strict` gate passed cleanly: validate-data, lint, format, 2660 tests, and production build.
