# 2026-06-24

## 14:49 — PR: Gate DELETE /games/:id behind MAP_EDITOR_ENABLED

This PR closes GitHub issue #648 (debt score 5), which flagged the `DELETE /api/v1/games/:id` route as an unguarded endpoint that any caller with a game UUID could use to permanently destroy a game and its Spaces-backed state object.

The original track spec proposed adding `requireSide` middleware — the same auth guard used on `GET /:id`, `GET /:id/actions`, and `POST /:id/actions`. During implementation it became clear that this was the wrong model: the DELETE endpoint exists purely as a dev and testing utility for clearing lobby state between sessions, and it carries no player-auth semantics. Fitting it into the `requireSide` pattern would have required callers to hold a valid sideToken for an active game, which would break the use case of deleting an `'open'` game before a second player has joined.

The correct fix is to make the endpoint invisible in production using the `MAP_EDITOR_ENABLED=true` flag, consistent with how the codebase already gates write operations on `moduleData.js` and the entire map-editor/scenario-editor/table-test toolchain. When the flag is absent the route returns 404 — the same response as a non-existent route — giving no information to a potential attacker about what endpoints exist. When the flag is set (development only), the route behaves exactly as before.

Test changes follow the same pattern as `moduleData.js`: existing DELETE tests are nested inside a `describe('when MAP_EDITOR_ENABLED=true')` block with `beforeEach`/`afterEach` hooks managing the env var, and a new top-level test confirms that `deleteGame` is never called and a 404 is returned when the flag is absent. The `afterEach` import was missing from the vitest import list and was added as part of fixing the lint error that surfaced during `quality:strict`.

Nothing about the actual deletion logic changed — the `getGame` existence check before touching Spaces remains, as does the idempotent Spaces-before-SQLite ordering. The `getGame` import (which had been temporarily removed during an intermediate attempt) was restored to its original position in the store barrel import.
