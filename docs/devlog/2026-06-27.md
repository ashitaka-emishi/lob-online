# 2026-06-27

## 03:59 — PR: M9 MOVE Action — Unit Movement Handler + Hex Control Wiring

This PR delivers the `MOVE` action handler, the first action in the engine that mutates unit
position on the game map. Before this work, units could be activated via `ACTIVATE_STACK`, engage
in combat and morale resolution, and end their activations — but had no way to actually move
between hexes. The MOVE action closes that gap, wiring together the pre-existing movement engine
(`engine/movement.js`) and the VP hex-control tracker (`engine/vp.js`) into a working dispatch
path.

The design went through a Checkpointed mode review before implementation began, which settled
three key decisions. First, `remainingMPs` lives on `UnitStateSchema` as an optional field
(absent until a stack is activated, then set by `handleActivateStack`). It's initialized in
`handleActivateStack` rather than at Activity phase start because that's the natural scope
boundary — MPs belong to an activation, not the entire phase, and initializing lazily avoids
iterating every unit on every phase transition. Second, `handleActivateStack` now accepts `ctx`
(scenario + OOB) to look up movement allowances by unit type: cavalry get `mounted` MPs, limbered
artillery get `limbered` MPs, unlimbered artillery get 0 (they can't move), and everything else
defaults to infantry `line` MPs. Third, path validation uses `movementPath` from the movement
engine rather than step-by-step cost computation — this means the handler validates that the
destination is reachable at optimal cost rather than trusting the client's specific path sequence,
which is consistent with how other handlers treat getValidActions candidates as "informational
only."

Two correctness details worth noting for future readers. The `movedThisActivation` flag on
`currentActivation` is set to `true` after every successful MOVE — this was not in the original
plan checklist but is required for the Opening Volley trigger (LOB §5.4), which fires when a
moving stack comes adjacent to an enemy before firing. Missing this flag would silently break
Opening Volley eligibility. The guard order in `resolveMove` also matters: "unit is in the active
stack hex" must be checked before "path starts at unit's current hex" because the path is
parameterized relative to the activation hex, not wherever the unit physically is; reversing the
order causes the wrong error code to surface.

Hex control wiring (SM §5.1 terrain VP) calls `updateHexControl` after every successful move. The
`isVpControlEligible` check inside `updateHexControl` requires an `oobUnit` with a known type to
grant control — when OOB data is absent, the unit is treated as ineligible rather than defaulting
to eligible. Tests for the VP path therefore supply a minimal OOB stub so the eligibility check
can resolve the unit as infantry. This is the correct production behavior: if OOB lookup fails, we
don't silently grant VP control.

Explicitly deferred: ZOC (Zone of Control) interaction during movement — LOB §4 defines ZOC
penalties for moving adjacent to or through enemy-occupied hexes, but this requires knowing which
hexes are enemy-occupied and the ZOC rules for each unit type. The handler currently computes
optimal path cost without ZOC penalties. This is a known gap to be addressed in a future track
once the MOVE path is proven stable.
