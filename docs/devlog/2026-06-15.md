## 00:22 — PR: M6 Debt Sprint + Combat Tests — security, a11y, store refactor, resolveMorale suite

This PR closes two parallel tracks from the M6 debt sprint: `m6-debt-sprint_20260614` (six discrete
debt items) and `m6-combat-tests_20260614` (the missing resolveMorale test coverage from PR #582).
Both were implemented simultaneously by parallel agents on a single feature branch with no file
overlap, then committed and verified together with a single `npm run quality:strict` pass.

The debt sprint addressed a diverse mix of concerns. The most architecturally interesting change was
`#583` — moving the scenario fetch from `GameView.vue`'s `onMounted` into `useGameStore.loadGame()`.
`GameView` was previously fetching scenario data independently using route params as the slug source,
which created a dual source-of-truth with the store. The fix co-locates all game-load side-effects
in the store and makes the fetch non-blocking (failure leaves `scenario` as `null` and `TurnControl`
degrades gracefully rather than breaking). The generation-counter pattern already in the store for
action-poll cancellation was extended to cover the scenario fetch, preventing stale responses from
a prior `loadGame` call from overwriting newer state.

The security items (#403, #350) were deferred at PR #582 time because they appeared to have M8
dependencies, but on inspection both are self-contained Express middleware additions. `helmet()` is
configured with a dev-mode CSP carve-out for `localhost:5173` so the Vite dev server's WebSocket
and HMR connections aren't blocked during development; production gets the full restrictive default.
The rate limiter is applied only to the two write routes that could be enumerated or abused (game
create and join), not to the full router, keeping read performance unaffected.

The combat test track fills the coverage gap left by PR #582's `resolveMorale.js` shipping without
a test file. The 729-line test module covers all six morale result codes (normal, shaken,
disorganized, routed, bloodlust, leaderCasualty), additive morale transition combinations per LOB
§6.2a, and all validation error paths. Critically, it also adds a seven-test dispatch integration
suite for the FIRE_COMBAT → RESOLVE_MORALE two-step: confirming the soft-lock (no valid actions
while `combatResult` is pending), the morale state update after resolution, and immutability of
the pre-resolution state object. All test fixtures are inline — no disk reads — using the same
injected-context pattern the production handlers use.

Deferred to the remaining M6 tracks: the four OOB editor bugs from #506 were listed in the
debt-sprint spec but those bugs had already been fixed in a prior PR (`eca067e`); the spec was
stale. The debt register sync registers #571–#581 under PR #582 but does not yet reflect the
net-score after tracks `m6-domain-bugs` and `m6-combat-wiring` land — that final update will
come in the last M6 sprint track.

## 01:40 — PR: M6 Combat Wiring — OOB Deduplication, Dispatch DI, Soft-lock Fix

This PR closes three M6 team-review findings (issues #571, #572, #573) that together make the
combat pipeline functional end-to-end in production. All three are addressed in a single commit
on `feat/m6-combat-wiring`. The prerequisite ordering is: OOB deduplication first (Phase 1), then
dispatch DI wiring (Phase 2), then the soft-lock fix (Phase 3) — each phase building on the
cleaner foundation left by the previous one.

Phase 1 (#573, debt score 2) extracted `findOobUnit()` from three separate inline definitions in
`fireCombat.js`, `closeCombat.js`, and `resolveMorale.js` into a single canonical export in
`engine/oob.js`. All three files had identical implementations with minor doc-comment variations;
the canonical version carries the union of all three LOB section citations. This is a pure
refactor — behaviour is unchanged — but it was listed as a prerequisite for #572 because the DI
seam fix needs a clean shared import surface.

Phase 2 (#572, debt score 4) wired the missing context object through the live dispatch call in
`server/src/routes/games.js`. The root cause was straightforward: `handleFireCombat` (and the
other combat handlers) accept `{ oob, scenario, mapData, hexIndex }` as a third argument and fall
back to synchronous disk reads plus Manhattan-distance approximation when that argument is absent.
The route layer was calling `dispatch(state, action)` with no third argument, so every live
`FIRE_COMBAT` call was silently bypassing real LOS and hex-distance checks. The fix loads all four
context values once before the dispatch call and threads them through. The `dispatch()` signature
in `engine/actions/index.js` was also updated to accept and forward `ctx = {}` to each handler
via the handler invocation line. Games route tests were updated to assert the three-argument call
shape including the ctx object.

Phase 3 (#571, debt score 4) fixed the soft-lock that prevents a player from taking any action
after `FIRE_COMBAT` or `CLOSE_COMBAT` sets a pending resolution. The bug was in `getValidActions()`
in `engine/actions/index.js`: after the `leaderCasualty` branch there was a catch-all
`if (state.pendingResolution !== null) return []` that returned an empty list for all other pending
types, including `combatResult`, `closingRoll`, and `moraleCheck`. The fix adds three explicit
branches before that catch-all, each returning `[{ type: 'RESOLVE_MORALE', payload: null }]`.
Three new tests in `index.test.js` cover the no-soft-lock assertion for each type; a stale test
in `resolveMorale.test.js` that had been asserting the old empty-list behaviour was updated to
match the corrected expectation. Total debt score removed by this PR: 10.
