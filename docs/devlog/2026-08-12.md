## 07:43 — South Mountain Map Data Recovery — Stash Integration (map-data-recovery_20260811)

Recovered a forgotten `git stash` entry from 2026-05-23 — `stash@{0}`, message "WIP: boundary
face fix (#418) + map session data — not committed to PR #451" — that had sat unapplied for
roughly two and a half months while the multi-module platform split and the M9 map-completion
work both proceeded from the old, much smaller base without knowing it existed. It held a
2261-hex `map.json` (0 unknown terrain, full playable-grid coverage) plus a real schema/engine
fix for a "boundary mirror faces" bug in the edge-ownership model: hexes on the true map
boundary have no neighbor to canonically own their faces 3-5, and the old schema simply
rejected that data outright.

The track ran five phases, each gated by a human checkpoint since it touched the rules-engine,
schema, and shared map-editor components (Checkpointed mode, High risk, per this repo's own
`agentic-quality-rails.md`). Phase 1 exported the stash to a durable location (a patch file and
a permanent `archive/stash-0-map-recovery` branch, both preserved rather than deleted — a git
branch costs nothing and the audit trail is worth more than the tidiness of removing it) before
touching anything, then diffed it against current `master` file-by-file rather than attempting
a blind `git stash apply` across 2.5 months of drift. The diff turned out unusually clean:
`map.schema.js` had zero other changes in that window, and every non-`hexes` field in
`map.json` was byte-identical between stash and current, so the data merge (Phase 3) was a
straightforward wholesale `hexes` replacement rather than a field-by-field reconciliation.

The client-side reconciliation (Phase 4) was the real judgment work: `MapEditorView.vue` alone
had a 249-line diff against the stash, almost all of it current's own independent evolution
(module-slug routing, an `EditorNav` component, a `beforeSave` hook for an unrelated
playable-boundary feature, an `EDGE_DISPATCH` refactor). Rather than reapplying any of that,
each file was checked function-by-function for whether it had its own hardcoded assumption that
only 3 canonical edge faces exist; two call sites in `MapEditorView.vue`
(`handleEdgeClearAll`, `handleHexEdgeClearAll`) did, and were the only functional changes made
there. `edge-model.js`'s `canonicalOwner()` got the actual bug fix; a related divergence in
`validateCoexistence` (stash used a `CONTOUR_TYPES`-based check, current uses a narrower,
later, independently-evolved `SLOPE_TYPES` check backing a separate `applyContourPaint` tool)
was deliberately left alone — reapplying the stash's older version would have been a
regression, not a fix.

A manual smoke test against a live dev server (Playwright) caught one more thing: the map
editor's reference-image path was still missing a `south-mountain/` subfolder segment from the
multi-module split, a bug that predates this track entirely but was invisible until the
recovered data actually needed the canvas to grow past its old 1400×900 fallback size. Fixed
with a quick confirmation; after the fix, a painted road rendered cleanly through the
newly-recovered eastern boundary hexes with zero console errors — direct, live confirmation
that the boundary-mirror-face fix actually works, not just that it compiles.

End state, verified against the live engine rather than re-asserted: all 10 of 10 scenario VP
hexes are now reachable by the movement pathfinder (was 4 of 10), elevation completeness rose
from 91.1% to 97.9%, and hexside feature coverage jumped from 156 to 777 hexes — enough that
issue #685 (the separate hexside-network visual audit and playtest) got a substantial,
unplanned head start, though it stays open since none of that has been spot-checked against the
source map image yet. `map.json`'s `_status` deliberately stays `"partial"` for the same
reason — this track fixed a data-coverage and reachability problem, not a
verification-completeness one. Issue #689 closed with the full account; 3252 tests passed
throughout, 0 regressions, `npm run build` succeeds.
