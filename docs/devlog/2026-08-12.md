## 08:49 — `/agent-teams:team-review` on PR #690: one real bug, one false narrative

Same three-dimension pattern as PR #687's review (security, performance, architecture), same
adaptation (no `Teammate`/`TaskCreate`/`TaskList` in this environment — three
`agent-teams:team-reviewer` agents spawned directly via `Agent`, consolidated by hand). This
time the architecture reviewer was explicitly briefed on the failure mode the last two review
passes kept catching — a claim true of the structure measured, overstated as a claim about the
real world — and told to re-verify everything against actual code and data rather than trust
the PR's own framing. It found four instances in one PR: two the security and performance
reviewers had already independently converged on from different angles, and two nobody else
was positioned to catch.

**The real bug, found by security and performance independently:** `validateBoundaryMirrorFaces`
opened with `if (!gridSpec) return`, and `gridSpec` is `.optional()` in the schema — so a
payload that simply omitted it let faces 3-5 through on _any_ hex, interior or not, with no
boundary check at all. A second, compounding hole: `hexNeighborInDir` returns `null` for any
hex ID outside the grid rectangle, so an out-of-grid ID read as an automatic "boundary" with no
bounds check, and calling it would permanently cache the ID in `hex.js`'s unbounded,
never-evicted `_parseCache`/`_formatCache` — a documented invariant ("callers must validate
against the map index first") that this new call site was the first to violate. Fixed: fail
closed when `gridSpec` is absent, bounds-check hex IDs against the grid with cheap string
parsing before ever touching the memoized helpers. Caught the same completeness gap in
`edge-strip.js` and its client mirror in `edge-model.js` — both only ever iterated canonical
faces 0-2, so a non-playable boundary hex's own faces 3-5 were never cleaned up. The existing
`isEdgeAtNonPlayableBoundary(hex, adjHex)` predicate already handled the boundary case
correctly once the loop bound widened — no new logic needed, just wider coverage. 7 new
regression tests across both fixes.

**The false narrative, found only by architecture:** the story that "the old schema simply
rejected [the recovered] data outright" doesn't hold — verified directly: both the stash's
original `map.json` and the merged result parse cleanly against the schema as it existed
_before_ this PR, because neither contains a single populated face 3-5. The schema widening
was bundled with the data recovery but wasn't required by it; it's forward-looking editor
capability, and nothing in the shipped map — or the manual smoke test that was described as
"live confirmation the fix works" — has actually exercised it against real persisted data. Also
caught, independently: `gridSpec` declares a 64-column grid but column 64 has zero hex records
in _every_ version of this data going back to the original stash, so "full playable grid
coverage" was never true (real: 2205/2240, 98.4%) — filed as #691, since it's unclear whether
that's a genuine gap or `gridSpec.cols` should be 63. And the "156 → 777 hexes" hexside-coverage
figure counted `edges: {}` scaffolding as coverage; the honest number is 0 → 757 real features,
which is a better result stated correctly rather than a worse one inflated.

Corrected in place across `map.json`, `docs/library.md`/`.json`, `docs/agents/domain-expert/design.md`,
`docs/designs/high-level-design.md` (including softening the risk register from `Resolved` to
`Reduced — Medium` — it named its own open sub-items in the same table cell), `CLAUDE.md`, and
this file's earlier entries today, rather than left as a silent correction only the PR diff
would show. Followed up on the already-closed #689 rather than letting the closing comment
stand uncorrected. 3259 tests green, 0 regressions.

## 18:25 — Column 64 Resolved (map-col64-investigation_20260812)

The session was interrupted mid-investigation on this track and resumed cold. Nothing was
lost — track state, git history, and the two PR #690 review agents spawned earlier were all
still intact. Resuming those two agents surfaced something worth recording: the extensive
follow-up fix pass described in the entry above had _already_ addressed everything they'd
independently found (the fail-open validation bug, the false "schema rejected it" narrative,
the ford/fence registry bug, issue #691 itself) before the interruption happened — both
agents' final reports were re-analyzing already-fixed code and recommending things already
done. Verified this directly against `origin/master` rather than trusting the agents'
self-correction notes, since they'd only seen partial context.

The actual investigation: does column 64 exist on the printed map, or is `gridSpec.cols: 64`
a calibration off-by-one? Queried the live Map Editor's own computed grid geometry directly
(the honeycomb-grid library's real output, not a hand-derived formula) — column 64's hex
bounding box sits at `x=3786.75`–`3867.75`, but the reference image is only 3804px wide. Then
cropped the raw image at that exact boundary across four rows spanning the full map height,
markers drawn in precisely rather than eyeballed. The user, mid-tool-call, suggested the right
answer before the evidence fully landed: "column 64 may not have been clickable or ever set
because it's a half hex on the map." Confirmed exactly that, consistently across all four
samples — real printed terrain extends through the boundary, but only the leftmost ~21%
(17.25px of 81px hex width) has any source pixels. The physical map sheet ends mid-hex.

Getting the resolution right took a second pass. The first instinct was to treat column 64
like the map's existing row 00/36 border markers — record it with `playable: false` and leave
`gridSpec.cols` at 64. That was wrong, caught before implementation: `playable` is checked only
by the edge-feature stripper, nowhere in the movement or reachability code. What actually
excludes rows 00/36 today is `gridSpec.rows: 35` bounding `hexNeighborInDir`'s search — a
structural exclusion, not a flag. Recording column 64 with a flag the engine doesn't enforce
would have left it reachable to the movement pathfinder despite being 79% nonexistent. Fixed
by correcting `gridSpec.cols` to 63 instead, which excludes column 64 through the same
mechanism already used for rows 00/36. `validate-data`'s grid-coverage check (added earlier
today) needed no code change — it resolved to a clean `2205/2205` (100%) automatically once
the constant was right. VP-hex reachability re-verified unaffected (still 10/10 — column 64
never had records to be reachable in the first place). 3259 tests, 0 regressions, build
succeeds. Issue #691 closed with the full account, including the correction.
